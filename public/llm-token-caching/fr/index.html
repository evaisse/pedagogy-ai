1 · Modèle mental

Un cache de LLM est surtout un cache de préfixe.

L’endpoint reçoit une longue suite de tokens. Si le début de cette suite est identique à un début déjà traité récemment, il peut réutiliser le travail effectué sur cette partie.

Le cache ne cherche pas une idée « proche ». Il reconnaît une entrée compatible selon les règles du fournisseur : même modèle, même endpoint ou configuration pertinente, même préfixe exploitable.

2 · Mécanisme

Le premier appel chauffe le chemin. Les suivants peuvent le reprendre.

Sur un premier appel, l’endpoint doit encoder et traiter tout le prompt. Sur les appels suivants, si le début reste identique, une partie du coût d’entrée et de la latence peut baisser.

La génération de sortie reste du vrai calcul. Le cache ne remplace pas le raisonnement ni les tokens produits par le modèle.

01

Cache froid

Tout le prompt est lu. Le préfixe peut être indexé pour plus tard.

02

Cache chaud

Le même préfixe revient. L’endpoint reprend le travail déjà disponible.

03

Suffixe nouveau

La demande, les diffs et les logs récents restent lus normalement.

3 · Pourquoi les agents de code en profitent

Un agent répète une grande base et ne change que le bord actif.

Dans une session de codage, la base stable est volumineuse : consignes système, règles du dépôt, définitions des outils, fichiers ouverts, plan courant. Le bord actif est plus petit : dernière commande, erreur de test, diff ou question de l’utilisateur.

Plus l’agent garde cette base stable au début du prompt, plus les tours successifs ont une chance de toucher le cache.

4 · Ce qui casse le cache

Un changement tôt dans le prompt coûte plus cher qu’un changement tardif.

L’idée pratique : placer ce qui bouge souvent après ce qui bouge rarement. Un agent efficace stabilise le préambule et pousse les informations volatiles vers la fin.

Aide le cache

Ordre stable des outils

Les schémas et noms d’outils restent dans le même ordre entre deux tours.

Casse tôt

Réécrire le système prompt

Une variation au début décale tout le préfixe exploitable.

Casse souvent

Contexte régénéré au hasard

Un tri non déterministe ou des résumés changeants réduisent les hits.

Dépend du fournisseur

TTL, modèle, routage

Durée de vie, granularité et facturation restent propres à chaque endpoint.

5 · Économie du cache

Écrire dans le cache et lire depuis le cache ne coûtent pas toujours pareil.

Tous les fournisseurs ne vendent pas le même compromis. Certains rendent le cache presque invisible : premier passage au prix normal, lectures suivantes moins chères. D’autres facturent explicitement la création ou la durée de vie du cache, parce que garder des états KV disponibles consomme de la mémoire ou du stockage proche des GPU.

Question de rentabilité

Combien de lectures faut-il pour amortir l’écriture ?

Si C est le coût input normal du préfixe, une lecture à 0,1C économise 0,9C par rapport à une relecture fraîche.

Une écriture premium à 1,25C s’amortit dès un hit. Une écriture à 2C demande plutôt deux hits. Avec du stockage TTL, ajoute le coût de stockage avant de décider.

Règle de poche

Pour un agent de code, le cache récompense la stabilité du préfixe.

  1. Garde les instructions, outils et règles du dépôt dans un ordre déterministe.
  2. Ajoute les informations nouvelles à la fin plutôt que de réécrire le début.
  3. Ne confonds pas cache et mémoire : le modèle ne « se souvient » pas, l’endpoint réutilise un calcul.
  4. Mesure toujours sur ton fournisseur : TTL, seuils et réductions varient.
