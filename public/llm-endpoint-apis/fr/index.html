Contrats d’API pour modèles LLM

L’endpoint que tu choisis décide de ce que ton application doit porter.

Chat Completions parle en messages. Responses parle en items et peut porter l’état, les outils et une part du raisonnement serveur. Les anciens endpoints restent utiles surtout pour comprendre les migrations.

Voir la carte Choisir un endpoint
Deux appels, deux contrats Chat Completions : une conversation en messages.
Méthode POST /v1/chat/completions
Entrée 
const completion = await client.chat.completions.create({
  model: "gpt-5",
  messages: [
    { role: "system", content: "You are a helpful assistant." },
    { role: "user", content: "Hello!" }
  ]
});
Sortie utile 
const text = completion.choices[0].message.content;

Tu reconstruis toi-même le tableau messages à chaque tour. C’est simple, portable et très compatible avec les gateways multi-fournisseurs.

Chapitre 01 · Situer

1 · Carte des contrats

Les APIs ne changent pas seulement l’URL. Elles changent le modèle mental.

Un endpoint LLM est un contrat entre ton application et le fournisseur : forme de l’entrée, forme de la sortie, responsabilité de l’historique, représentation des outils et garanties disponibles.

Point de vocabulaire « Compatible OpenAI » signifie souvent compatible avec /v1/chat/completions. Cela ne garantit pas que /v1/responses, les outils hébergés ou les conversations serveur soient disponibles.

Chapitre 02 · Lire la forme

2 · Messages vs items

Chat ressemble à une transcription. Responses ressemble à un journal d’exécution.

Dans Chat Completions, l’unité centrale est le message : rôle, contenu, parfois des appels d’outils collés à la réponse assistant. Cette forme est excellente pour un chatbot classique.

Dans Responses, l’unité centrale est l’item. Un message est un item, mais un appel de fonction, une sortie d’outil ou un bloc de raisonnement en sont aussi. L’API décrit mieux ce que le modèle fait, pas seulement ce qu’il dit.

Si ton UI doit montrer les étapes d’un agent, une liste typée d’items est plus lisible qu’un seul message enrichi.
Deux structures La même demande, deux lectures différentes.

Chat Completions

system Instructions user Question assistant Réponse + tool_calls

Le fil est naturel à relire, mais l’application doit assembler le prochain tour.

Responses

message reasoning function_call function_call_output message

Le fil devient une trace typée : l’UI et le backend savent distinguer parole, action et résultat.

3 · État conversationnel

Le vrai coût d’un chatbot multi-tour est souvent le transport de l’historique.

Avec Chat Completions, l’endpoint est stateless : ton application stocke la conversation, compacte si besoin, puis renvoie le contexte utile au prochain appel.

Avec Responses, tu peux encore tout gérer côté client, mais tu peux aussi chaîner avec previous_response_id ou utiliser une conversation persistante. L’état devient une option de plateforme.

Nuance importante Stateful ne veut pas dire obligatoire. Pour certaines contraintes de rétention, il faut désactiver le stockage ou utiliser les mécanismes prévus par le fournisseur.
Simulateur pédagogique Qui transporte l’historique ?
Payload renvoyé 5.1k
État côté serveur 0

En mode Chat, la charge visible côté client grandit avec la conversation : tu renvoies les messages utiles à chaque tour.

4 · Outils et raisonnement

Les agents font apparaître la différence entre « texte de réponse » et « trace d’action ».

Un appel d’outil n’est pas une phrase normale. Il a un nom, des arguments, un identifiant de corrélation et une sortie. Plus ton produit expose d’actions, plus la structure du contrat devient importante.

Chat Completions sait faire du function calling, mais l’orchestration reste surtout dans ton backend. Responses rend la boucle plus explicite et ajoute des primitives pour les outils hébergés, MCP, le code interpreter, la recherche et les modèles de raisonnement.

Boucle d’outil Le même geste, deux responsabilités.

Chat Completions

  1. Le modèle renvoie un message avec tool_calls.
  2. Ton backend exécute l’outil.
  3. Tu ajoutes le résultat dans messages.
  4. Tu rappelles le modèle.

Responses

  1. La sortie contient des items typés.
  2. function_call et function_call_output restent corrélés.
  3. Les outils hébergés peuvent réduire les allers-retours.
  4. Le raisonnement peut persister sans exposer la chaîne brute.

5 · Portabilité

Le choix technique dépend aussi de ton écosystème de fournisseurs.

Si tu veux basculer entre plusieurs endpoints « OpenAI-compatible », Chat Completions reste souvent le plus petit dénominateur commun. Si tu construis une expérience agentique centrée sur OpenAI, Responses donne accès aux primitives les plus récentes.

Contrat Point fort Risque à gérer
/v1/chat/completions Interopérabilité, intégrations simples, contrôle manuel du contexte. Historique, compaction, outils et état restent à orchestrer côté app.
/v1/responses Items typés, état serveur, outils hébergés, raisonnement et multimodalité. Support moins universel hors OpenAI ou gateways qui l’implémentent vraiment.
/v1/completions Compatibilité avec de vieux prompts et quelques modèles historiques. Modèle mental trop pauvre pour les nouveaux chatbots et agents.
Assistants API Historique d’objets assistant, threads, fichiers et runs. API dépréciée côté OpenAI : planifier la migration vers Responses et Conversations.

6 · Choisir

Le bon choix se lit dans le workflow, pas dans le nom du modèle.

Pars du besoin opérationnel : portabilité, état conversationnel, outils, conformité, migration. Le modèle peut rester le même pendant que le contrat d’API change autour de lui.

Recommandation

Chat Completions

Utilise Chat Completions si la priorité est de rester portable entre fournisseurs et de garder le contrôle complet du contexte côté application.

Ce que tu gagnes
Une forme de requête largement supportée.
Ce que tu assumes
La mémoire, la compaction et la boucle d’outils.

Règle de poche

Plus le workflow devient agentique, plus le contrat doit décrire des actions plutôt que du texte.

  1. Besoin portable et simple : commence avec Chat Completions.
  2. Besoin d’outils, d’état serveur ou de raisonnement persistant : regarde Responses.
  3. Besoin de conformité stricte : vérifie explicitement le stockage, la rétention et le mode stateless.
  4. Ancien Assistant : migre par flux nouveaux vers Responses et Conversations, puis backfill si besoin.
